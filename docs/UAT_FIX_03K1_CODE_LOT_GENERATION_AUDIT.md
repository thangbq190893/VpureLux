# UAT Fix 03K.1 - Business Code and Lot Number Generation Audit

## 1. Executive Summary

This is a docs-only audit and design note for business code and lot-number generation. No production code, Domain/Application/DB/schema/migration files, posting logic, FIFO logic, costing logic, or UI behavior were changed.

Current finding:

- Product code, Vật tư/Component code, Customer code, Warehouse code, receipt lot number, and adjustment-increase lot number are user-entered today.
- CustomerGroup code is also user-entered through Application/API contracts and seed data, but no dedicated Razor page was found under `Pages/Customers`.
- Sales order number, Sales line number, BOM version number, and pricing version numbers are already system-generated through existing domain/repository logic and should not be replaced by this batch.
- Existing business-code fields are generally immutable after creation: update DTOs and edit pages do not expose code editing.
- Existing DB unique indexes and domain/repository duplicate checks are the final safety layer for the main code fields.
- Inventory lot uniqueness is currently scoped to `(WarehouseId, StockItemId, LotNo)`, so a global daily lot sequence is possible but the existing DB protection is not global.

Recommendation:

- Introduce a later shared Application-level generator for create/post commands only.
- Use `{PREFIX}-{yyyyMMdd}{sequence:D4}`.
- Use Redis as a daily cached counter, protected by ABP distributed lock.
- Treat Redis as an accelerator, not source of truth.
- If Redis key is missing, seed from DB by `MAX` numeric suffix matching `{PREFIX}-{yyyyMMdd}%`.
- Keep DB uniqueness/domain duplicate checks and add bounded retry on collision.
- Do not allocate codes on page GET.

## 2. Current Manual Code/Lot Fields

Manual fields found in create/post flows:

- Product `Code`: `CreateProductDto.Code`, `Catalog/Products/Create`, `CreateModal`.
- Vật tư/Component `Code`: `CreateComponentDto.Code`, `Catalog/Components/Create`, `CreateModal`.
- Customer `Code`: `CreateCustomerDto.Code`, `Customers/Create`, `CreateModal`.
- CustomerGroup `Code`: `CreateCustomerGroupDto.Code`, Application/API/seed path; no dedicated Razor page found.
- Warehouse `Code`: `CreateWarehouseDto.Code`, `Inventory/Warehouses` inline create form.
- Inventory receipt `LotNo`: `ReceiptLineInput.LotNo`, `Inventory/Receipt`.
- Inventory adjustment increase `LotNo`: `AdjustmentModel.CountAdjustmentLineInput.LotNo`, transformed to `ReceiptLineInput.LotNo` for positive deltas in `Inventory/Adjustment`.

Other document-number-like fields found:

- Sales `OrderNo`: generated by `SalesManager` using `SO-{yyyyMM}-{sequence:D6}` and `AppNumberSequences`.
- Sales line `LineNo`: generated inside `SalesOrder.AddLine()` and renumbered on removal.
- BOM `VersionNo`: generated per product through `IBomVersionRepository.GetNextVersionNoAsync`.
- Pricing `VersionNo`: generated per product/component through pricing repositories.
- Inventory `ReferenceType` / `ReferenceId` / `BomVersionId`: technical references passed by posting services or app services, not normal user-entered business numbers in the Web UI.
- `IdempotencyKey` / confirmation idempotency keys: technical hidden/system keys, not business codes.
- Customer `TaxCode`: manually entered legal/tax identifier; should remain manual.

## 4. Existing Uniqueness/Domain/DB Protections

Catalog:

- Product and Component constructors require nonblank code.
- `CatalogManager` checks repository `CodeExistsAsync` before creating Product/Component.
- EF configuration has unique indexes on Product `Code` and Component `Code`.
- Update DTOs do not include code, and edit pages render code disabled/read-only.

Customers:

- Customer and CustomerGroup normalize codes to uppercase.
- Managers check repository `CodeExistsAsync` before creation.
- EF configuration has unique indexes `UX_Customers_Code` and `UX_CustomerGroups_Code`.
- Update DTOs do not include code; edit UI shows code disabled/read-only.

Inventory:

- Warehouse normalizes code to uppercase and checks `CodeExistsAsync`.
- EF configuration has unique index `UX_Warehouses_Code`.
- InventoryLot requires nonblank `LotNo`.
- EF configuration has unique index `UX_InventoryLots_WarehouseId_StockItemId_LotNo`.
- Receipt and adjustment-increase lines require `LotNo`.

Sales:

- `SalesManager` already generates `OrderNo` as `SO-{yyyyMM}-{sequence:D6}`.
- `EfCoreSalesOrderRepository.GetNextOrderSequenceAsync` uses SQL Server `MERGE ... WITH (HOLDLOCK)` against `AppNumberSequences`.
- `SalesOrderConfiguration` has unique index `UX_SalesOrders_OrderNo`.

Infrastructure:

- The app already configures `AbpDistributedCacheOptions.KeyPrefix = "VPureLux:"`.
- Web/Web.Public modules configure Redis-backed distributed locking through `IDistributedLockProvider`.
- Web tests replace distributed lock/cache with in-memory implementations.

## 5. Recommended Generated Fields

Recommended for generation in later coding batches:

- Product `Code`.
- Vật tư/Component `Code`.
- Customer `Code`, if business accepts generated customer codes.
- Warehouse `Code`, if business accepts generated warehouse/location codes.
- Receipt `LotNo`.
- Adjustment positive-delta `LotNo`.

Recommended first wave:

- Product: lower business risk, high frequency, clear prefix.
- Vật tư/Component: lower business risk, high frequency, clear prefix.
- LotNo: high UAT value, but needs more care because supplier/manufacturer lot numbers may be meaningful.

Recommended second wave:

- Customer and Warehouse after business confirms whether existing codes are human-assigned external identifiers.

## 6. Fields That Should Remain Manual or Overrideable

Remain manual:

- CustomerGroup `Code`: small master-data set such as `RETAIL`/`DEALER`; often semantically meaningful.
- Customer `TaxCode`: legal/tax identifier.
- Sales override reason, adjustment reason, source/reference technical fields: not sequence fields.
- BOM/Pricing version numbers: already domain-generated per parent.
- Sales `OrderNo`: already generated and protected; changing it is a separate business decision.

Overrideable with permission/policy:

- Product/Vật tư/Customer/Warehouse codes during imports or data migration.
- LotNo when supplier/manufacturer physical lot number must be preserved.

If override is allowed, the create command should still run the same duplicate check and DB unique index should remain the final guard.

## 7. Prefix Recommendation

| SequenceName | Prefix | Field |
|---|---|---|
| `Product` | `PROD` | Product code |
| `Material` | `MAT` | Vật tư/Component code |
| `Customer` | `CUS` | Customer code |
| `Warehouse` | `WH` | Warehouse code |
| `InventoryLot` | `LOT` | Receipt/adjustment lot number |

Notes:

- `MAT` is recommended for Vật tư because user-facing Vietnamese uses `Vật tư`; backend identifiers should remain `Component`.
- `WH` is short and familiar for warehouse/location codes.
- CustomerGroup prefix is intentionally not recommended unless generation is later approved.

## 8. Daily Sequence Format

Required format:

```text
{PREFIX}-{yyyyMMdd}{sequence:D4}
```

Example for July 6, 2026:

```text
PROD-202607060001
PROD-202607060002
MAT-202607060001
LOT-202607060001
```

Sequence reset scope:

- Reset per `SequenceName`/prefix/date.
- Date should come from the application clock (`IClock`) and be consistently interpreted in the app's business timezone.
- Do not derive the date from browser input or user-local JavaScript.

## 9. Redis Cache Strategy

Recommended abstraction:

```text
IBusinessCodeGenerator
GenerateAsync(sequenceName, prefix, date, existsAsync)
```

Recommended logical cache key:

```text
VPureLux:Sequence:{SequenceName}:{yyyyMMdd}
```

Cache value:

- Latest allocated integer sequence for that `SequenceName` and date.
- Example: after generating `PROD-202607060002`, value is `2`.

Important behavior:

- Redis is not source of truth.
- Redis key missing/null/deleted must not reset to 1 blindly.
- On missing Redis value, seed from database using max existing suffix for the same prefix/date.
- Consider setting expiry longer than one day, for example 2-7 days, so late requests/retries still see the same date's counter.

ABP key-prefix note:

- The app already configures `AbpDistributedCacheOptions.KeyPrefix = "VPureLux:"`.
- Implementation should avoid accidental double-prefixing if using `IDistributedCache`/ABP cache wrappers. The design key above is the intended physical/logical Redis namespace; coding batch should verify exact ABP cache key composition.

## 10. ABP Distributed Lock Strategy

Recommended lock key:

```text
VPureLux:SequenceLock:{SequenceName}:{yyyyMMdd}
```

Lock behavior:

- Acquire lock before reading/seeding/updating the Redis counter.
- Keep the critical section small:
  - read cached counter;
  - seed from DB if missing;
  - increment;
  - check collision through `existsAsync`;
  - write latest allocated value;
  - release lock.
- Use ABP's distributed lock provider already configured with Redis in Web/Web.Public and in-memory lock in tests.
- Do not rely on per-process `lock` or static counters because the app can run multiple instances.

## 11. DB Seed Strategy When Redis Is Missing

For each generated field, seed with:

```text
MAX numeric suffix where Code/LotNo LIKE '{PREFIX}-{yyyyMMdd}%'
```

Examples:

- Product: query Products where `Code` starts with `PROD-20260706`, parse final 4+ digits, take max.
- Vật tư/Component: query Components where `Code` starts with `MAT-20260706`.
- Customer: query Customers where `Code` starts with `CUS-20260706`.
- Warehouse: query Warehouses where `Code` starts with `WH-20260706`.
- LotNo: query InventoryLots where `LotNo` starts with `LOT-20260706`.

Fields that can seed safely by date:

- New generated Product/Component/Customer/Warehouse codes once they follow the date prefix.
- New generated LotNo once it follows the date prefix.

Fields that do not currently store date-compatible codes:

- Existing legacy/manual Product/Component/Customer/Warehouse codes.
- Existing manual LotNo values.
- CustomerGroup codes.
- Sales `OrderNo`, because it uses a monthly `SO-{yyyyMM}-{D6}` format and an existing DB sequence table.

Seed behavior with legacy data:

- Ignore non-matching legacy/manual values for the generator seed.
- Continue relying on final duplicate check/DB unique index for full safety.

## 12. Why MAX Suffix Is Safer Than COUNT

Use MAX suffix, not COUNT.

Reasons:

- Manual/deleted/imported data can create gaps; COUNT would reuse an existing suffix after gaps.
- Collisions may occur if rows exist outside normal create flow.
- Multiple prefixes share a date; COUNT can be wrong if filtering is not exact.
- Existing codes may have been migrated or manually edited before generation exists.

Example:

- Existing codes: `PROD-202607060001`, `PROD-202607060003`.
- COUNT returns 2, so next would be 3 and collide.
- MAX suffix returns 3, so next is 4.

COUNT is not recommended for this design.

## 13. Collision/Retry Strategy

Even under a distributed lock, generation should be defensive:

1. Acquire lock for sequence/date.
2. Get cached latest; if missing, seed from DB max suffix.
3. Candidate = latest + 1.
4. Format code.
5. Call `existsAsync(candidate)`.
6. If exists, increment and retry.
7. Save latest allocated number to Redis.
8. Return candidate.
9. On final create/post, keep existing domain/repository duplicate checks and DB unique indexes.

Recommended retry limit:

- Start with 10-20 attempts.
- If exhausted, throw a friendly business exception instructing the user to retry.

DB duplicate handling:

- Product/Component/Customer/Warehouse code unique indexes should remain final safety.
- Inventory lot DB uniqueness is currently warehouse/item/lot scoped, not global; if a global lot sequence is used, generator collisions should be checked globally by LotNo prefix, but existing DB safety will only catch duplicate lot in the same warehouse/item.
- Do not add schema changes in this audit; if global LotNo uniqueness is required, it is a deferred DB decision.

## 14. UI Behavior Recommendation

Create pages:

- Do not allocate code on GET.
- Hide or disable the code field by default.
- Show placeholder/help text such as `Tự động sinh khi lưu`.
- If override is approved, expose an optional manual field or "Nhập mã thủ công" advanced toggle with permission/policy.

Edit/detail/list:

- Show generated code read-only.
- Do not allow editing generated code after create unless a separate rename workflow is approved.

Receipt/Adjustment lot number:

- For normal flow, show LotNo as auto-generated on save.
- If supplier/manufacturer lot must be captured, provide a separate optional "supplier lot" concept later, or allow manual LotNo override only with clear policy.
- Do not generate lot number for zero/negative adjustment rows.
- Generate LotNo only for receipt-like/increase lines that will create `InventoryLot`.

## 16. Risks and Deferred Decisions

Risks:

- Existing manual data may not match the new date-prefix format; seeding must ignore it safely.
- Redis outage or cache deletion can cause collisions if DB seed is wrong.
- Global lot generation may not align with supplier/manufacturer lot tracking.
- Customer and warehouse codes may be external/business-owned identifiers in some deployments.
- ABP cache key prefixing must be verified to avoid unexpected physical Redis keys.
- Sales already has a DB-backed monthly sequence; mixing sequence strategies without documentation could confuse future maintainers.

Deferred decisions:

- Whether Product/Vật tư/Customer/Warehouse manual override is allowed and who can use it.
- Whether CustomerGroup codes should ever be generated.
- Whether InventoryLot should eventually have global LotNo uniqueness.
- Whether supplier/manufacturer lot should be a separate field from internal generated LotNo.
- Whether Sales OrderNo should remain monthly DB-backed or later align to daily Redis generator; this audit recommends leaving it unchanged.
- Whether generated code date should use tenant-local business date if multi-tenant timezone settings appear later.
